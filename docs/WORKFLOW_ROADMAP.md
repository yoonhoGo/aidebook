# 업무·할 일·일정·대시보드 로드맵

작성: 2026-09-23. 상태: 계획, 구현 미착수.

## 목표와 첫 출시 범위

하나의 업무에서 미팅 일정 → 회의록 → 테크스펙 → 작업 티켓 → GitHub PR → 티켓 완료 → 작업 내용 노트를 이어 간다. 대시보드는 오늘의 일정과 할 일, 막힌 업무, 다음 행동을 보여주고 필요한 시점에 알린다.

첫 출시는 캘린더 1종 읽기, 로컬 할 일과 개인 작업 계획, 기존 Obsidian·Confluence·Jira·GitHub 자료 연결, 수동 관계 설정, 시간 알림, 회의록·작업 기록 템플릿을 포함한다. 모든 단계가 필수인 선형 프로세스를 강제하지 않는다. 하나의 회의에서 여러 업무가 생기거나, 티켓 하나에 여러 PR이 연결되는 흐름을 지원한다.

AI 추출·초안은 후속 단계다. 외부 티켓 생성·상태 변경, 외부 문서 자동 저장, 원격 실시간 알림 서버는 별도 확장으로 둔다. 이 문서는 개발 계획이며 구현·외부 변경을 실행한 기록이 아니다.

## 현재 기반과 우선순위

- 기존 Rust Core, SQLite, SourceRef/Snapshot, 메모·관계·근거·검토 후보, 공통 IPC/CLI/MCP와 연결 registry를 재사용한다.
- 기존 업무 UI의 식별자와 로컬 저장 데이터를 조사한 뒤 영속적인 업무 모델로 연결한다. 기존 자료를 자동 삭제하거나 같은 제목만으로 합치지 않는다.
- 일정·할 일·알림의 전용 모델과 대시보드 조회 모델은 추가 작업이다. 기존 알림 설정 UI가 실제 예약·전달을 증명하지 않는다.
- 기존 구현의 native/live 미검증 항목은 [구현 상태](IMPLEMENTATION_STATUS.md)를 따른다. 이번 첫 출시에서 사용하는 경로는 실제 환경 인수 검증에 포함한다.
- W0 → W1 → W2 → W3 → W4 → W5가 첫 출시 순서다. 이후 W6, 별도 범위가 확정되면 W7을 진행한다. Jev 검토는 계속 최후순위다.

## 제품·데이터 계약

| 개념 | 책임과 주요 필드 |
| --- | --- |
| 업무 `work_items` | 안정적 ID, 제목, 목적, 상태, 완료 조건, 필요한 산출물 |
| 할 일 `tasks` | 로컬 행동 또는 외부 티켓 참조, 담당자, 기한, 개인 우선순위, 상태 |
| 작업 계획 `task_time_blocks` | 할 일 참조, 예정 시작·종료; 한 할 일에 여러 작업 시간 허용 |
| 일정 `calendar_events` | 연결·캘린더·외부 ID, 시작·종료, 시간대, 종일 여부, 반복 회차 식별, 취소 상태 |
| 관계 `work_links` | 업무·할 일·일정·문서·티켓·PR 참조, 관계 종류, 근거, 작성 주체, 확정 여부 |
| 알림 `reminders` | 대상, 예약 시각, 예약 식별자, 버전, 다시 알림, 취소·처리 상태 |
| 활동 `activity_events` | 대상, 이전·다음 상태, 발생 시각·수집 시각, 작성 주체, 중복 방지 키 |

위 이름은 설계안이다. W0에서 기존 스키마와 관계 API를 조사해 확정한다. 문서 본문·원본·메모 이력을 중복 저장하지 않고 기존 저장 구조를 참조한다. 파생 그래프와 사용자 확정 관계는 구분한다.

### 상태와 소유권

- 업무 기본 상태: 예정 → 진행 중 → 완료 검토 → 완료. 보류·취소 및 재오픈을 지원한다. 막힘은 이유를 가진 별도 속성으로 둔다.
- 로컬 할 일: 예정·진행 중·완료·취소. 외부 티켓은 원본 상태와 정규화된 표시 상태를 함께 보존하며 알 수 없는 상태를 임의로 완료 처리하지 않는다.
- 외부 티켓의 제목·상태·담당자·기한은 원본 소유다. 개인 우선순위·작업 예정 시간·개인 알림은 로컬 소유다. 개인 목표일이 필요하면 원본 기한과 별도 필드로 둔다.
- 같은 외부 티켓은 공급자·계정·범위·외부 ID를 기준으로 중복 방지하며 여러 업무에서 참조할 수 있다.
- PR 병합, 티켓 완료, 업무 완료는 독립적이다. 모든 필수 완료 조건을 확인해 업무 완료를 제안하고 사용자가 확정한다. 작업 기록 저장 여부도 별도 표시한다.
- 수정은 버전 검사와 멱등성 키로 보호한다. 원격 갱신이 개인 계획과 사용자 메모를 덮어쓰지 않는다.
- URL·티켓 키·사용자 지정 연결을 우선한다. 유사 제목이나 AI 추론은 제안으로만 표시하고 자동 확정하지 않는다.
- 연결 해제·권한 철회 시 원본 접근을 차단하고 마지막 확인 시각을 표시하되 사용자 메모와 계획은 보존한다.

## 화면과 행동

### 대시보드

| 영역 | 내용 | 기본 행동 |
| --- | --- | --- |
| 오늘 | 시간순 일정·작업 시간, 오늘 마감 | 일정 열기, 회의록 작성, 작업 시작 |
| 다음 행동 | 직접 고정한 일, 임박한 일, 진행 가능한 일 | 계획하기, 완료하기 |
| 확인 필요 | 기한 초과, 리뷰 대기, 막힘, 완료 검토 | 이유 확인, 다시 알림, 해당 없음 |
| 진행 중 업무 | 상태, 다음 행동, 최근 결정, 티켓·PR | 업무 상세 열기 |
| 최근 완료 | 결과와 미작성 작업 기록 | 기록 남기기 |

초기 정렬은 사용자 고정 → 기한 초과 → 기한 임박 → 개인 우선순위로 결정적으로 계산하고 이유를 보여준다. 일정은 시간순으로 유지한다. 빈 상태, 연결 실패, 오래된 데이터, 로딩 상태를 각각 표시한다.

대시보드는 Core의 조회 결과로 만들고 별도의 업무 상태 사본을 저장하지 않는다. 목록은 페이지 단위로 조회하고 변경 후 재조회한다. 업무 상세는 요약·다음 행동·자료·타임라인을 제공하며 관계 그래프는 보조 탐색으로 사용한다.

### 흐름별 지원

1. 미팅 전: 일정에서 관련 업무, 지난 회의록, 미해결 질문을 연다.
2. 미팅 후: 일시·참석자·업무 링크가 채워진 회의록 템플릿을 작성한다.
3. 설계: 결정 사항을 테크스펙에 연결하고 범위·완료 조건을 기록한다.
4. 실행: 티켓과 PR을 수동 또는 명시 링크로 연결하고 상태를 갱신한다.
5. 완료: 완료 조건을 검토하고 결과·판단 이유·검증·남은 과제를 기록한다.

업무별로 필요한 산출물을 선택한다. 회의록이나 스펙이 필요 없는 업무는 `해당 없음`으로 처리해 반복적인 누락 경고를 막는다.

완료 기준: 첫 출시 시나리오가 실제 환경에서 통과하고 [구현 상태](IMPLEMENTATION_STATUS.md)에 테스트 명령·환경·결과·미지원 동작을 기록한다. fixture나 브라우저 데모만으로 native/live 완료를 선언하지 않는다. 배포는 기존 서명·공증·패키징 출시 조건도 충족해야 한다.

- [ ] 테크스펙·작업 기록 초안 및 일일 요약 생성.
- [ ] 근거 위치와 사용 자료 버전 표시, 수정·거절·재생성 지원.
- [ ] 기존 후보 검토 구조 재사용; 사용자 작성 부분을 자동 덮어쓰지 않음.

완료 기준: 한국어·한영 혼합 대표 사례에서 누락·잘못된 담당자/기한·잘못된 연결을 평가한다. 초안 확정 전 외부 변경이나 업무 자동 완료가 없고 모델 실패 시 수동 흐름을 계속 사용할 수 있다. 모델 선택·자료 전송 범위·비용은 이 단계 착수 전에 결정한다.

### W7 — 선택적 외부 실행

의존성: W5 및 외부 쓰기 범위 확정. AI 없이도 실행 가능.

- [ ] 티켓 생성·상태 변경, 캘린더 수정, 문서 저장 중 우선 동작 하나 선택.
- [ ] 읽기와 쓰기 권한 분리, 대상 계정·프로젝트·필드 변경 미리보기.
- [ ] 사용자 실행, 원격 버전 충돌, 중복 요청, 부분 실패·재시도 처리.
- [ ] 결과 원본 ID를 다시 읽어 로컬 업무와 연결하고 실행 이력 보존.

완료 기준: 동일 요청 재시도 시 외부 자료를 중복 생성하지 않고, 결과가 불명확한 요청은 원격 결과 확인 후 재시도한다. 사용자에게 실제 적용 결과와 실패한 부분을 구분해 보여준다.

## 일정 산정과 작업 기록

W0에서 캘린더 인증과 macOS 알림·프로세스 수명을 확인하기 전에는 달력 날짜로 출시를 약속하지 않는다. 이후 각 단계의 저장/Core, UI, 연결, native 검증 작업량을 나눠 산정한다. 첫 사용 가능한 중간 결과는 W2이며, 전체 첫 출시는 W5 통과 시점이다.

구현 시 단계별로 작은 jj 변경을 만들고 시작/종료 상태를 확인한다. 완료한 체크박스에는 검증 문서와 change ID를 연결한다. 기능 구현 완료, 로컬 자동 검증 완료, native/live 인수 완료를 별도로 기록한다. 이 문서 작성은 어느 단계의 구현 완료도 의미하지 않는다.
